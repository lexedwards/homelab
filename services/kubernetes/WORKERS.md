# Worker Operations

One optional Rocky Linux 10 amd64 worker belongs on each of `compute` and `store`.
The default allocation is 4 vCPU, 8 GiB RAM and a 64-GiB OS disk per worker. CPU
type `host` exposes nested virtualization capabilities; it does not enable missing
host firmware/KVM support. Workers are protected full clones, not live-migratable
Intel/AMD peers. Their OS disks are replaceable; application data belongs off-node.

## Ownership And Inputs

`workers.tf` owns VMs and snippets in the existing cluster root/state. The empty
`workers` default preserves the server-only deployment. Enable both physical-host
entries using the input example: unique VM IDs/short names, explicit OS FQDNs,
secondary bridges and a service VLAN distinct from the primary VLAN. Supply
`store` host/upload/datastore inputs too. Existing server resources and
configuration remain unchanged.

Each worker's required `fqdn` must be a lowercase DNS name whose first label
matches `name`, without a trailing dot. Cloud-init receives both `hostname` and
`fqdn`; Rocky's native FQDN preference selects the explicit OS identity rather
than an inherited name. RKE2 keeps `name` as its explicit short Kubernetes node
name. Do not use the stable API alias as a worker's identity.

Choose FQDNs privately within `api_dns.zone`. The root manages an A record for
each worker using its observed primary DHCP lease and the shared `api_dns.ttl`.
Guest-agent interfaces are matched to the first Proxmox NIC by MAC, not interface
array order. Missing or ambiguous primary leases and internal pod/Service
addresses prevent publication. Service-VLAN leases never supply worker DNS.

Set `worker_reverse_dns_zone` privately only after confirming this root may own
worker PTR records in that existing octet-aligned IPv4 reverse zone. Otherwise
leave it `null`; A records are still managed. The root never creates DNS zones.
PTR names reverse the observed primary addresses and point to the managed worker
FQDNs. An address change replaces the old owned PTR; disabling PTR management
plans deletion of this root's PTRs, not the zone or unrelated records.

Before applying, check existing A/CNAME/PTR records and DHCP DNS ownership. Import
records deliberately assigned to this root instead of managing the same record
from two states or competing with DHCP updates. `overwrite = false` preserves
other records in the RRset; it is not proof of exclusive ownership or absence of
conflicting addresses. `manage_etc_hosts` changes only the guest hosts file.

Before an authorized plan, reconfirm IDs, template provenance, cross-node full
clone support, bridge tags, nested KVM, datastore content/capacity and DHCP/DNS.
Earlier approvals/proofs are not current reservations. Plan/apply only from
canonical `main` with the established production state. Inspect for unchanged
server/etcd ownership and no replacement of existing resources. Apply requires
separate authorization. Infrastructure apply neither enrolls workers nor deploys
platform manifests. Inspect sensitive `worker_dhcp_leases` privately: addresses
are matched to Proxmox-owned NIC MACs. Reserve both leases upstream before
enrollment, normal workloads or maintenance. Neither MACs nor addresses are inputs.

For existing workers, adding DNS ownership needs a reviewed DNS-only plan, not a
VM replacement. It must leave all VM/snippet resources and the API record
unchanged. After an approved apply, query the upstream DHCP DNS servers directly
for worker A records and any managed PTRs before enrollment. Do not use the DNS
administration HTTPS endpoint as a DNS listener or the guest hosts file as proof.
Changing a reservation or replacing a worker requires rechecking the observed
primary lease and the DNS plan; reservations remain upstream/operator-owned.

## Native Network And First Boot

The Q35/VirtIO layout uses `ens18` for node/API traffic and `ens19` for the service
network. Both obtain IPv4 addresses from DHCP. Pods receive no direct LAN/VLAN
interfaces; there is no Multus.

Cloud-init network-data owns only `ens18`. Upstream cloud-init 25.3's Rocky
NetworkManager renderer silently ignores secondary DHCP route/DNS overrides.
Instead, cloud-init writes native `kubernetes-service.nmconnection`: secondary
DHCP, `never-default`, ignored automatic routes/DNS, disabled IPv6 and higher
autoconnect priority than autogenerated profiles. Automatic profile creation is
disabled for `ens19`. Connected-subnet reachability remains. No script patches
generated profiles, sets MACs, writes discovered node IPs or restarts interfaces.

First boot installs signed, exactly pinned RKE2 agent/common/SELinux RPMs from
persistent EL10 repositories, the distribution kernel/modules and NFS client tools.
It records the installation boot ID and enables the agent. Cloud-init reboots into
the installed kernel; NetworkManager loads the secondary profile on that reboot.
Bootstrap networking before it is not accepted as dual-NIC readiness. The agent
is gated on installation success and a separately enrolled token file.

Before enrollment, verify that both the static and running OS hostname equal the
configured FQDN after the kernel reboot, while RKE2 `node-name` retains the short
name. Check upstream DNS separately; the guest hosts file alone is not proof.
Updating a cloud-init snippet does not rename an existing guest or rerun first
boot. For workers created without `fqdn`, populate the new required private
input and obtain approval for a reviewed worker replacement to qualify clean
boot. Do not rerun cloud-init or replace/rename the initialized control plane as
part of this worker change.

RKE2 natively selects the default-route interface. Enrollment requires the reboot,
one IPv4 default route on `ens18`, no IPv6 default route and one DHCP IPv4 address
per NIC; it checks the resulting Kubernetes InternalIP. Revalidate interface names
if image/PCI layout changes. On failure investigate DHCP/layout, not static-IP or
SELinux-bypass workarounds.

## Enroll One Worker

Keep the server/recovery token in verified-HTTPS external OpenBao plus independent
Proton Pass custody. The default `agent-token` can alias it; do not distribute that
recovery credential as a routine worker token.

Enrollment uses a separate native secure CA-pinned bootstrap token, default
bootstrap privileges and a 30-minute TTL per attempt. Tokens are not bound to a
particular node name. Native bootstrap Secrets intentionally exist in the
control-plane datastore and remain sensitive; this is unrelated to disabled
workload Secret synchronization.

After authorized provisioning and reservations, run from a trusted workstation:

```bash
python3 scripts/enroll-worker.py \
  --server-ssh '<admin>@<server-address>' \
  --worker-ssh '<admin>@<worker-primary-address>' \
  --identity-file '<approved-private-key>' \
  --server-known-hosts '<reviewed-server-host-keys>' \
  --worker-known-hosts '<reviewed-worker-host-keys>' \
  --node-name '<worker-name>' --host '<compute-or-store>' \
  --api-server 'https://<stable-api-name>:6443'
```

Host keys must already be reviewed; new keys are never accepted automatically.
Noninteractive sudo is required on the intended guests, not an OpenBao admin
token. `--expected-version` defaults to `v1.36.6+rke2r1`; supply the corresponding
reviewed version if RPM pins change. `--timeout` defaults to 600 seconds (30–900
accepted), plus up to 60 seconds for revocation cleanup.

`--node-name` is the short RKE2 name, not the OS FQDN. Worker preflight compares
it with the OS hostname's first label and requires an exact RKE2 `node-name`
match. Verify the full configured OS FQDN before enrollment as described above;
this command does not validate its DNS suffix or upstream DNS records.

The command refuses existing node identities, agent certificates and token files.
It transfers credentials through subprocess stdin over pinned SSH, exclusively
creates root-only mode-0600 `/etc/rancher/rke2/join-token`, restores its label and
starts the agent. Values never enter argv, OpenTofu, cloud-init or normal output.
Readiness checks worker role/zone/version, primary address and Cilium while
preserving existing node UIDs and the control-plane taint. Actual etcd membership
is a separate acceptance check, not proven by a Ready API.

Success/failure both attempt deletion of the owned token by non-secret ID. If
connectivity fails during minting before that ID is received, TTL is the backstop.
Never log token-create output or JSON token lists: they can expose credentials.
The worker file remains for native startup syntax/CA pinning after revocation;
reconnect is intended to use its enrolled client certificate/node password.
Verify service and guest restart after revocation before claiming independence.

On failure inspect protected cloud-init/kernel, DNS, TCP 9345/6443, agent journals,
node-password and Cilium diagnostics. Do not blindly overwrite a token file,
delete credentials or rerun first-boot installation. Deliberately reconcile a
failed pre-certificate attempt before issuing another short-lived credential.

## Install And Qualify Kata

`platform/kata.yaml` is a separately invoked RKE2 Helm-controller lifecycle, not
an OpenTofu provisioner. It selects stock Kata 4.3.1 `clh-runtime-rs` with Cloud
Hypervisor, SELinux, existing overlayfs and external virtio-fs. Other shims and
snapshotter installation are disabled. Runtime/dispatcher/kubectl images are
digest-pinned. The versioned chart archive was reviewed with SHA-256
`c25077416d37c178bf72df0204ea3ba89418efad1b1299b0d5d34ec02556187e`;
its URL is a version pin, not controller-enforced checksum validation.

The stock installer requires privileged host access for binaries/configuration
and modules; workloads receive no such permission or custom SELinux allow rule.
It selects workers and processes one at a time. Its credential-bearing dispatcher
targets the tainted control plane: verify its
`node-role.kubernetes.io/control-plane=true` label before applying. Install jobs
can restart agents/containerd. Explicitly authorize disruption and initially
install before accepting applications. Do not cordon all workers before the Helm
install job has somewhere to run. Later upgrades require a reviewed per-worker
drain and installer-target procedure, not unattended runtime upgrades.

After authorization with the verified administrative kubeconfig:

```bash
kubectl apply -f platform/kata.yaml
kubectl -n kube-system wait job/helm-install-kata --for=condition=complete --timeout=900s
kubectl -n kata-system get jobs,pods
kubectl get runtimeclass kata-clh-runtime-rs -o yaml
```

The stock installer owns persistent RKE2 containerd integration; never edit
generated `config.toml`. Inspect persistent template/drop-ins and effective CRI:
ordinary default must remain `runc`, with the designated handler selecting the
Rust shim/Cloud Hypervisor. A package or label is not VM-backed execution proof.

RuntimeClass scheduling requires the installer label plus admin-controlled
`homelab.node-restriction.kubernetes.io/kata-verified=true`. Cloud-init never sets
that protected label. Per worker, cordon it, verify KVM/configuration/SELinux,
provisionally set the verification label and run an explicitly node-bound
synthetic isolated pod while still cordoned. Inspect the Rust shim, actual Cloud
Hypervisor executable/process label, `/dev/kvm` use, networking and intended
volumes. Remove the label and keep the node cordoned on failure; uncordon only
after success. Workloads/kubelets must not be permitted to grant that label.
Repeat after replacement and runtime changes.

`examples/workloads.yaml` has ordinary/explicitly isolated Deployments with worker
selectors and hostname spread. Apply only under runtime-test authorization; prove
both Intel/AMD execution and pod/HTTP connectivity, not just Ready status. Without
verified eligibility isolated pods must remain Pending; missing handlers must
fail sandbox creation, never fall back to runc. Delete the example namespace
afterwards. Record evidence in ALE-29, not a permanent migration-test harness.

Root-filesystem examples are not production NFS or workload-secret qualification.
TrueNAS export/permissions, CSI/Retain, OpenBao workload auth/reviewer lifecycle,
application reload and socket/MCS limits still need approved qualification. A VMM
label alone does not establish complete socket separation. Never weaken SELinux
or introduce a custom Kata build to hide failure.

## Maintenance And Replacement

1. Confirm API/recovery access, remaining capacity, replicas, PDBs and storage.
2. Cordon/drain one worker with a bounded timeout. Respect PDBs and StatefulSet
   semantics; do not force-delete workloads or local data without approval.
3. For restart, verify post-revocation restart/reboot, unchanged node UID/primary
   lease, Cilium and runtime configuration before uncordoning.
4. For replacement, remove verified eligibility, stop the old VM and deliberately
   remove its Kubernetes Node so RKE2 can reconcile its node password. Never run
   duplicate identities. Review protection changes and a saved replacement plan
   for only that worker, not server/peer. Managed OS/EFI/cloud-init disks can be
   deleted; they are not PV storage.
5. Review the replacement's SSH key/new Proxmox MACs, reserve observed leases and
   enroll with a fresh credential. Re-run job-mode Kata installation through a
   reviewed Helm update; a completed one-shot dispatcher does not cover new nodes.
6. Requalify runtime/volumes before restoring verified eligibility. Check original
   control-plane UID and sole etcd member/cluster IDs, ordinary scheduling, both
   VLAN gateways, API TLS and Cilium. Inspect remaining platform Helm convergence.

One worker is not an availability guarantee: replicas share a host, and drain,
capacity or PDB constraints can prevent maintenance. `store` loss leaves the API
on `compute` but can remove TrueNAS data. `compute` loss removes the API and its
worker; existing `store` pods may continue without automatic rescheduling or
guaranteed service reachability. NFS is not storage HA; etcd snapshots omit PV data.

Measure bounded drained reboot/replacement and inspect stuck Kata shim/VMM/virtio-fs
processes. Slow undrained shutdown remains unqualified; do not turn that gap into
a hard-reset policy. Local checks imply no deployment, rollout, restore or
disruptive test authorization.
